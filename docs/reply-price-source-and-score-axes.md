# 담당 ② 답신 — 가격 소스와 점수 축

2026-09-20. `전체 프로젝트 현재 실황`의 제안과 11번 항목에 대한 답입니다.

---

## 1. yfinance 지적은 맞습니다. 다만 소스를 바꿔도 안 풀립니다

Yahoo 약관을 확인했습니다 — "personal, royalty-free, **non-transferable**, **revocable**,
non-exclusive license". 지적하신 대로 외부 사용자에게 보여주는 서비스에는 부적합합니다.

**그런데 무료 대안이 전부 같은 제약입니다.** 직접 쳐보고 확인했습니다:

| 소스 | 무료 한도 | 결과 |
|---|---|---|
| Stooq | 키 불필요 | **봇 차단(JS 챌린지)**. 프로그램 접근 불가 |
| Alpha Vantage | 하루 25콜 | 5,800종목이면 232일 |
| Polygon (현 Massive) | 5콜/분, 2년 | 약관에 **"Individual use"** — 같은 문제 |
| EODHD | 하루 20콜 | 논외 |
| Marketstack | 월 100콜 | 상용은 별도 협의 |

즉 **소스 교체로 푸는 문제가 아니라, 공개 시점에 유료 라이선스를 사거나
서비스 형태를 바꿔야 하는 문제**입니다. TradingView 위젯은 *표시*를 해결하지만
점수용 데이터는 해결하지 못합니다 — 지적하신 그대로입니다.

### 그래서 지금은 아무도 안 막힙니다

`contracts/db_schema.sql`의 **`price_snapshot` 테이블이 이미 격리 경계**입니다.
엔진은 가격이 어디서 왔는지 모릅니다. 나중에 소스를 바꿔도 점수 엔진·의견 생성·UI는
한 줄도 안 바뀝니다. 바뀌는 건 담당 ①의 수집 스크립트뿐입니다.

**프로토타입은 yfinance로 진행하고, README에 "공개 전환 시 교체 필요"를 명시하는 것**을
제안합니다. 지금 유료 결정을 하면 프로토타입이 멈춥니다.

### 필요한 양은 생각보다 훨씬 작습니다

"5,800종목 일봉 3년치"가 아닙니다. 쪼개보면:

| 용도 | 필요량 | 언제 |
|---|---|---|
| PER·PBR 백분위 | **전종목 최신 종가 1일치** | 하루 1회 배치 |
| `flag.ma_late` 배지 | 110일 히스토리 | **조회된 종목만**, 요청 시점 |
| 차트 표시 | 없음 | TradingView 위젯이 직접 가져감 |

그리고 **시가총액의 절반은 SEC가 공짜로 줍니다.** 확인했습니다:

```
dei:EntityCommonStockSharesOutstanding
AAPL 14,594,180,000주 · 2026-07-17 기준 · 이력 70건
```

`market_cap = 발행주식수 × 종가` 이므로, **라이선스가 필요한 건 종가 하나뿐**입니다.
전종목 종가 1일치면 대부분의 유료 플랜에서도 가장 싼 구간입니다.

## 2. 점수 축 (11번) — 5범주 20%씩은 권하지 않습니다

제안하신 5범주 중 **셋은 저희가 이유를 대고 일부러 뺀 것들**입니다.
README에 근거가 적혀 있습니다.

### 거시 — 점수의 재료가 아니라 읽는 법입니다

금리 하나 올랐다고 5,800종목 점수가 동시에 내려가면 **종목 비교 도구로서 쓸모가
없어집니다.** 어제 72점이던 종목이 오늘 65점인데 회사는 아무것도 안 변한 겁니다.
거시는 화면 상단 컨텍스트와 LLM 의견 문장에서 다룹니다.

### 차트(모멘텀) — 백테스트로 기각했습니다

20/60/110 이동평균으로 초기 모멘텀을 잡을 수 있는지 대형주 50종목 10년으로
종목별 부호검정했습니다:

```
초기 정배열 > 정배열 아님   :  14/50   p=1.000
전환 중(20>60, 60<110) > 하락 :  22/50   p=1.000

종목별 60일 선행수익률 중앙값:
  하락 (20≤60)           4.35%   <- 가장 높음
  정배열 초기 (0-10일)     2.98%
  정배열 성숙 (91일+)      0.83%   <- 가장 낮음
```

**이동평균이 위로 정렬될수록 이후 수익률이 낮았습니다.** 점수에 넣으면 많이 오른
주식에 높은 점수가 붙고, 초보자가 그걸 보고 고점에 들어갑니다.
대신 방향을 뒤집어 `flag.ma_late` 경고 배지로 씁니다.

(한계는 명시합니다: 대형주 50개·생존편향·상승장. "모멘텀은 없다"는 일반 명제가
아니라 *단일 종목 MA 배열 타이밍*이라는 특정 구현이 기각된 것입니다.)

### 검색 노출빈도 — 모멘텀과 정확히 같은 덫입니다

검색량이 많은 종목에 높은 점수가 붙으면 **밈주식이 상위권이 됩니다.**
초보자 보호 제품에서 정확히 반대 방향입니다.
실무적으로도 Google CSE 하루 100회면 5,800종목 1회전에 **58일**이 걸립니다.

### 상장폐지 위험 — 축이 아니라 배지여야 합니다

"상폐 점수 2점"은 초보자에게 **낮은 점수**로 읽힙니다. 실제 뜻은 *아예 피해야 할
종목*입니다. 20% 가중치로 희석하면 나머지 80%가 좋을 때 종합점수가 멀쩡해집니다.
그게 제일 위험합니다.

## 3. 그런데 부실 예측 작업은 버리면 안 됩니다

Altman Z''·Piotroski F·Sloan + 상장폐지 1,103건 라벨링(bankruptcy 152 /
listing_deficiency 110)은 **저희 쪽에 없는 진짜 자산**입니다.

**제안: 그 작업을 `flag.delisting` 배지의 내용물로 씁니다.**

지금 배지는 "Form 25 접수됨"이라는 이진값입니다. 담당 ①의 모델을 쓰면 이렇게 됩니다:

```
현재 : [경고] 2025-03-14 상장폐지된 종목입니다
이후 : [경고] 이 회사는 최근 상장폐지된 회사들과 재무 패턴이 비슷합니다
              (Altman Z'' 1.2 · Piotroski 3/9 · 유사 사례 262건 중 상위 8%)
```

이게 훨씬 강한 제품 기능입니다. 그리고 **점수의 재현성을 안 깨뜨립니다** —
배지는 경고이지 점수가 아니니까요. 축 4개는 그대로 두고 배지만 똑똑해집니다.

필요한 계약 변경은 `flags[]` 항목에 필드 몇 개 추가하는 정도입니다.
합의되면 제가 계약을 고치겠습니다.

## 4. 14번 (FastAPI vs stdlib) — 지금은 stdlib이 낫습니다

엔드포인트가 둘(`/api/score`, `/api/opinion`)뿐이라 의존성 2개를 더할 이유가 없고,
담당 ③가 `pip install` 없이 바로 띄울 수 있습니다. 엔드포인트가 늘거나 인증·검증이
필요해지면 그때 옮기면 됩니다. 지금 옮기는 건 이른 최적화입니다.

## 5. DB 통합 (12번) — 이미 되게 해뒀습니다

DuckDB를 SQLite로 바꾸라는 게 아닙니다. 분석용 저장소와 서빙용 저장소는 역할이 다릅니다.
필요한 건 내보내기 한 단계뿐이고, **참고 구현을 실제 SEC 2026q1으로 돌려서 확인했습니다**:

```bash
python etl/export_to_contract.py --from-zip 2026q1.zip --out data/stocks.db
python scoring/check_db.py data/stocks.db
```

```
companies            4,244
facts               68,115
liabilities_filled   1,130
```

`_read_zip()`만 DuckDB SELECT로 바꾸면 됩니다. 나머지는 그대로 돌아갑니다.

**변환에서 조용히 틀리는 세 곳** (전부 실데이터로 확인, 에러가 안 나서 위험합니다):

- **`qtrs`** — `0`은 시점 값(자산·부채·자본), `4`는 연간 기간 값(매출·이익·현금흐름)
- **`segments`/`coreg`** — 비어 있는 행만 (이미 알고 계신 부분)
- **`cik` 패딩** — SEC는 `'6955'`, 계약은 `'0000006955'`.
  안 맞추면 계약의 `sources` 필드가 깨져 좌측 드릴다운이 원본을 못 찾습니다

그리고 제가 틀렸던 것 하나: `liabilities` 폴백을 "KO 같은 일부 회사"라고 적었는데
**4,244개 중 1,130개(27%)** 였습니다. 예외가 아니라 기본입니다.
